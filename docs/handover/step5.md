## Things a later step will want to know

- **Only this step writes `user.role`.** `lib/services/roles.ts` `changeRole` / `decideVerification` update the column, write an audit row (`verification.*`, `user.role.*`, target = the user id) and a `role` / `verification` notice in one transaction. The role history is those audit rows (`roleHistory`).
- **Threshold figures** (`roleMetrics`): public, not deleted, not taken down Rees; ready sources in them (trash excluded); "被他人提问" = `message` rows with role `ree` for those Rees in conversations whose `user_id` is not the owner; feedback = `ree_feedback` rows (step 4's table, read as `message_id, user_id, vote 'up'|'down'`) on those messages from other users. Tables other steps create (`ree_feedback`, `payout`) are looked up with `to_regclass` once, so the code runs before and after they exist.
- **Step 6, payouts**: `hasOpenPayout()` in `lib/services/roles.ts` is the checkpoint for "有进行中提现的用户不能设为官方". It reads `payout` (`user_id`, `status in ('pending','approved')`) as soon as that table exists; until then everyone has none. If step 6 names the statuses differently, change that one query. The integration test creates a minimal `payout` table only when none exists.
- **Step 6, user detail**: `/admin/users/[id]?tab=kyc` and `?tab=payouts` are empty states; the users list's KYC column and filter read `none` for everyone (`AdminUserRow.kyc`), and filtering by any other KYC state returns nothing. Replace both once `kyc_record` exists. `PAYOUT_MIN_CREDITS` is in `lib/constants.ts`; the dashboard's payout guide reads it and links to `/settings?tab=billing` (there is no `/settings/identity` yet).
- **Sidebar data** comes from step 4's `components/shell/workspace-frame.tsx`; the unread-notice count is passed there.
- **Statistics sources of truth**: a successful answer is a `query_base` ledger row with `ree_id` (count distinct `ref_id` per Ree), so clearing a test conversation keeps the usage; a saved record is an answer message still on file; income is `query_fee_earned` with `ree_id`. `addGrant()` gained an optional `reeId` for that last one — step 4 should pass it when crediting an owner. An official owner's income is hidden on the user side and shown in the console.
- **`ree_moderated_private_check`** (in 0006): `moderated_at is null or not is_public` -- no writer can publish a taken-down Ree.
- **Takedown** (`takeDownRee`): `is_public = false`, `moderated_*` set, the Ree removed from other users' `conversation_ree` (history kept), owner notified. `updateRee` keeps a moderated Ree private whatever the owner sends. Restore makes it public again (prototype "恢复公开"). Takedown calls step 4's `detachRee(tx, reeId, { includeOwner: false })` inside its transaction and `refreshProfile(reeId)` after it (the profile goes, so the Ree leaves explore); restore calls `refreshProfile` to rebuild it. A model failure while rebuilding is logged and does not undo the decision.
- **Re-embed** (`lib/services/reembed.ts`): starting the job leaves the old entry enabled; batches fill `chunk.embedding_next` with the candidate; sources stored meanwhile use the old model and join the queue; the last step takes an exclusive advisory lock (`re0:embedding-switch`), locks `chunk`, checks every row has a candidate vector, then swaps the columns and the enabled entry in one transaction. `processKnowledge` takes the same lock shared and re-embeds if the model changed under it. Failure clears `embedding_next` and keeps the old entry. Work runs in `after()` steps of ≤ 4 minutes, one runner at a time: a runner claims the job through its heartbeat (compare-and-set), renews it before each batch and releases it at the end of its step; the models page polls `GET /api/admin/models/reembed`, which starts the next step once the job is released (or silent for 6 minutes); progress is counted per batch, not by recounting `chunk`. After the switch the runner rebuilds step 4's knowledge profiles (`ree_profile_vector`) with the new model, and the cron finishes any it did not reach. The candidate entry cannot change model or endpoint while its job runs; `/api/cron/reembed` (every 10 minutes; the project already runs step 4's hourly cron) is the backstop. Other instances may keep the old embedding model for up to the 60 s `modelFor` cache after the switch (proposal §7 sets that cache).
- **Model call log**: `lib/infra/ai/usage.ts` wraps every generation model (`languageModel()`), and `embedTexts` / `transcribeAudio` record their calls in `model_call`. Generation reports use per-call price snapshots; the overview sums those saved costs. `MODEL_PRICES` remains only for estimates of other model kinds.
- **Generation call reports**: `/admin/model-calls` and `/admin/model-calls/[id]` expose administrator-only statistics, filters (UTC+8 period, model, Free/Plan audience, purpose, status), per-attempt details and CSV export. Migration `0017_generation_call_reports` extends `model_call` with user/audience/purpose snapshots, outcome, latency, endpoint/request ID and exact decimal cost/rate snapshots. Each provider attempt, including a retry, error or interrupted stream, is counted separately. Gateway generation models automatically read input/output quotes from `https://ai-gateway.vercel.sh/v1/models`, cached for 60 seconds; actual Gateway response bills take precedence, otherwise quote-based calculations are explicitly labelled as estimates. Manual rates never override Gateway quotes, and static generation price tables are not used. Custom generation models have editable input/output prices in `/admin/models` (USD per million tokens, converted exactly to per-token prices); these share the existing endpoint/model rate store with `/admin/pricing`, including its transaction lock, audit trail and price revisions. Both custom prices must be supplied or both cleared. Prices may be updated for active configurations without changing their endpoint or model. Missing prices/usage remain unknown, and estimated totals are separate from known costs. Generation rates affect reporting only; customer answer credits remain fixed. Legacy context/status remains unknown. Missing historical costs can be estimated from recorded tokens at current prices with `npx tsx scripts/backfill-generation-costs.mts` (dry-run), then `--apply`; optional `--model=MODEL` and `--before=ISO` bound the selection. The backfill snapshots rates with a `backfill:` revision, labels rows as historical estimates, writes an audit record and preserves all existing costs and customer credits. Ambiguous model endpoints, missing rates and incomplete usage are skipped. Configuration changes never rewrite saved historical prices. Log writes are awaited but fail open so reporting cannot fail a generation request.
- **Generation audiences**: migration `0015_generation_audiences` adds `model_config.enabled_plan`; `enabled` selects the Free model and `enabled_plan` selects the Plan model. Each slot is unique and can share a configuration. Existing active generation configurations are initially enabled for both audiences. `/admin/models` switches each slot independently through `POST /api/admin/models/[id]/activate` with `{ audience: 'free' | 'plan' }` (omission means Free). `generationForUser(userId)` checks the current active subscription for answers, suggested questions and video generation; answers use the asking user's membership, owner operations use the owner's. Each slot has its own endpoint cache and falls back to the existing generation environment configuration when unset. A configuration active in either slot cannot change model or endpoint.
- **Administrators**: adding one creates a row with no password (`password_hash = ''`, status "invited") and returns a sealed link `/admin/login?invite=…` (7 days, single use) for the inviter to pass on. Nobody disables themself or the owner.

## Gotchas found

- **Import only packages listed in `package.json`.** Vercel installs with pnpm (strict `node_modules`), so a package that is only a dependency of a dependency is not importable there even though npm hoists it locally. `next build` passed here and failed on Vercel over `@ai-sdk/provider` (a dependency of `ai`); `lib/infra/ai/usage.ts` now derives those types from `ai` (`Extract<LanguageModel, { specificationVersion: 'v4' }>`). If you do add a dependency, update both `package-lock.json` and `pnpm-lock.yaml`.
- **Preview databases clear themselves on a journal mismatch.** drizzle's migrator applies only files whose journal `when` is later than the newest applied row and records each file by the sha256 of its text. A preview copy that ran a migration the branch later rewrote (here: 0006 before merging step 4's 0005) can never catch up. `db:prepare-preview` now also clears the preview copy when an applied hash is not in `db/migrations` or a local file would be skipped (`scripts/migration-journal.mts`, tested in `tests/unit/migration-journal.test.ts`); all the old guards still apply. A new migration's `when` must be later than every earlier one's.

- `./scripts/test-integration.sh` always uses the container `re0-test-pg` and ports 5439/5440; two sessions running it at once kill each other's database. I ran a copy with another container name and ports from my scratchpad.
- Two dev servers on `localhost` with different ports share the `re0_session` cookie and clear each other's (step 4's note); use `127.0.0.1:<port>` for one of them.
- `listHref` writes parameters in a fixed order so URLs are canonical (tests compare them).
