# Team Ree 实现方案

2026 年 11 月 6 日 · 待实施

## 1. 首版范围

用户可以在现有创建向导选择「个人 Ree」或「Team Ree」。Team Ree 创建后默认私有，创建者（Creator）仍由 `ree.ownerId` 表示。协作资格按 Ree 授予。Creator 可以定向邀请用户，也可以在发布后开放申请。加入的成员共享知识库，可以新增知识、维护自己的贡献，并在独立的测试会话里验证回答。

首版支持文本、文档、公开单页和 GitHub 仓库。成员获得的是贡献权限。成员启用的合规知识处理就绪后可直接影响公开 Ree 的回答，邀请和审批界面应写明这一点。Creator 负责 Ree 设置、公开范围、发布、定价、删除、成员管理和收益。所有权转移、团队积分池、知识逐条审批和已有 Ree 转为 Team Ree 留待后续设计。

## 2. 邀请、申请与审批

| 场景 | 操作人 | 生效规则 |
| --- | --- | --- |
| 发出邀请 | Creator | 定向邀请已注册账号。接收者收到站内通知，登录后可接受或拒绝。接受即成为成员，Creator 可在接受前撤销，超时的邀请可重新发起。 |
| 申请加入 | 已登录的非成员 | 仅已发布且开启招募的 Team Ree 接受新申请。公开页展示申请入口、申请状态和可选的申请说明。申请人在待审期间可撤回。 |
| 审批申请 | Creator | 在「成员」页批准或拒绝。批准时写入成员资格并通知申请人，拒绝时可附说明。受邀人或申请人在加入前只可查看 Ree 名称、Creator 名称和本人的流程状态及说明。 |
| 退出或移除 | 成员本人或 Creator | 成员可以主动退出，Creator 可以移除任一成员。重新加入走新的邀请或申请。 |

邀请绑定站内 `user.id`。首版可按完整邮箱精确查找已注册账号。现有账号身份按登录提供方和提供方账号 ID 区分，同一邮箱匹配多个账号时，Creator 须确认具体账号后再邀请。查找结果限量，邀请和申请按发起人限流。

邀请状态为 `pending`、`accepted`、`declined`、`revoked`、`expired`。申请状态为 `pending`、`approved`、`rejected`、`withdrawn`。同一 Ree 和同一用户最多一条待处理记录。Creator 邀请时遇到待审申请，界面引导处理该申请。用户申请时遇到待接受邀请，界面引导处理该邀请。过期邀请在发起新操作前由服务端关闭。

停止招募或取消发布会关闭新申请入口。Creator 仍可处理已有申请和向私有 Team Ree 发出定向邀请。Ree 被删除或管理员下架时，阻止新加入及成员写入。成员资格还要求账号启用，提交接受或批准时由服务端复核。

同一事务内完成状态变更、有效成员写入和站内通知。批准和接受可安全重试，重复请求返回已处理状态。邀请撤销与接受、申请撤回与批准、加入与移除按同一个 Ree 的锁顺序执行，先提交的状态决定后续操作结果。站内通知复用 `notify()` 和现有未读提醒，消息跳转到对应邀请、申请或成员页，目标页面独立校验权限。参见[现有审批事务](../lib/services/roles.ts)和[站内通知](../lib/services/notices.ts)。

## 3. 知识条目权限

| 操作 | Creator | 当前成员对自己的条目 | 当前成员对他人的条目 |
| --- | --- | --- | --- |
| 查看、预览、下载共享知识 | 可以 | 可以 | 可以 |
| 编辑内容、改名、移动、启停、移入回收站、恢复 | 可以 | 可以 | 只读 |
| 重新处理 | 可以，外部来源仍须通过发起人的授权检查 | 可以，外部来源仍须通过发起人的授权检查 | 只读 |

每个当前成员都可以新增知识。新增时由服务端将会话用户写入 `knowledge.createdBy`，后续编辑和重新处理均保留原贡献者。Creator 有权维护所有条目，包括已退出成员贡献的条目。其他成员可整理自己的条目并创建目录。共享目录的重命名和删除由 Creator 负责，因为删除目录会把其中全部知识移到「未分组」，包括回收站条目。

将 Ree 的访问权限和知识条目的写权限分别校验。`ownedRee()` 继续用于 Creator 专属操作，新增 Ree 成员授权和按知识条目判断的 `canEditKnowledge`。服务端从会话获取操作者，同时校验 Ree、条目、成员资格与贡献者。覆盖页面及接口中的列表、详情、子内容、文本预览、原文件下载、目录、单条和批量操作。文件继续通过现有鉴权路由从私有存储读取。参见[归属校验](../lib/services/rees.ts)、[知识接口](../app/api/rees/%5Bid%5D/knowledge/route.ts)、[原文件下载](../app/api/rees/%5Bid%5D/knowledge/%5Bkid%5D/file/route.ts)和[批量操作与目录](../lib/services/knowledge-library.ts)。

所有写操作在提交事务中复核成员资格。批量操作锁定并校验全部目标，遇到越权或失效条目时整批拒绝。将单条接口可组合提交的改名、移动、启停也放到同一授权与写入事务。列表展示贡献者和可操作状态，「全选」只选可写条目。成员的测试会话复用现有的 `userId + reeId` 隔离，读取会话、发送消息和清空历史时均校验当前资格。普通对话仍按 Ree 的公开状态和现有对话规则判断是否可提问。参见[测试会话](../lib/services/chat.ts)和[消息接口](../app/api/chats/%5Bid%5D/messages/route.ts)。

## 4. GitHub 凭据与处理任务

### 4.1 谁授权、谁付费

| 动作 | GitHub 授权账号 | 积分账户 |
| --- | --- | --- |
| 成员首次导入 GitHub 知识 | 发起导入的成员自己的 GitHub 连接 | 发起成员 |
| 贡献者重新处理自己的 GitHub 知识 | 该成员自己的 GitHub 连接 | 发起成员 |
| Creator 重新处理任何 GitHub 知识 | Creator 自己的 GitHub 连接，且该账号须有仓库读取权限 | Creator |
| 同一次任务延后执行或后台重试 | 该次任务记录的授权账号及连接版本 | 该次任务原有的积分冻结 |

仓库选择器已经按当前登录用户的连接列出仓库。提交时服务端仍要验证发起人、条目权限及仓库读取权限。后台处理当前通过 Ree 的 `ownerId` 取凭据，应改为通过该次处理任务记录的授权账号取连接。任务保存授权账号 ID 和连接版本，成员发起的任务还记录对应的成员资格记录 ID。访问令牌由现有加密连接表持有。Creator 的管理权允许编辑条目、启停和删除，重新拉取需要自己的仓库授权。参见[仓库选择接口](../app/api/auth/%5Bprovider%5D/repositories/route.ts)、[GitHub 连接](../lib/services/connections.ts)和[知识处理](../lib/services/knowledge.ts)。

后台领取任务时复核授权账号、连接版本和成员资格，读取仓库时检查实际访问权限，提交处理结果前再次验证任务仍有效。断开连接、替换连接、失去仓库访问权限或成员资格撤销都会使对应的旧任务失效。处理失败时释放本次冻结，保留已有的成功快照。首次导入没有成功快照时标为失败，并显示可操作的重新授权提示。由有条目编辑权、且有仓库访问权限的人发起新任务恢复处理。

知识导入和重新处理的成本记录同时保留 Ree 归属与实际发起人，冻结、结算和释放以该次任务的 `credit_hold` 为准。测试问答由测试者支付基础费，公开问答的查询费收入记到 Creator。内部测试按 `ree_test` 区分，排除在外部提问和收益指标之外。参见[知识成本记录](../lib/services/knowledge.ts)和[回答结算](../lib/services/answer.ts)。

### 4.2 私有仓库与公开边界

私有仓库首版仅允许导入私有、未发布的 Team Ree。导入前提示贡献者，抓取后的快照会共享给该 Ree 的当前成员。来源记录持久化仓库可见性，未知可见性按私有处理。发布前需要停用或移入回收站所有私有或未知的 GitHub 知识。发布、启用、恢复和处理结果提交等写入路径都应执行这一规则，包含批量设置与管理员恢复发布。发布与知识可见性变更按相同的 Ree 锁顺序提交。

公开问答、引用、发现检索、简介向量和展示在公开页的建议问题均使用同一公开资料过滤规则。重新处理时重新读取仓库可见性，发现仓库改为私有时先从公开检索剔除该来源并刷新衍生数据。首版以最近一次校验到的可见性为准，GitHub 侧变更会在下次校验时生效。参见[发布服务](../lib/services/rees.ts)、[管理员恢复](../lib/services/admin-rees.ts)、[公开发现检索](../lib/services/explore.ts)和[简介索引](../lib/services/profile.ts)。

## 5. 成员退出和移除后的处理

1. **撤销资格。** 记录 `revokedAt`、操作人和退出方式。事务提交后，后续请求失去该 Ree 的工作区、文件、编辑及测试会话权限。该 Ree 从「与我协作」移除，已有公开页和普通对话继续根据公开状态判断访问。
2. **保留已贡献的知识。** 条目、文件、最近成功的快照、贡献者标记和账务历史保留，仍适用原来的共享与发布规则。Creator 可以修改、停用、移入回收站或恢复这些条目。原贡献者再次加入后恢复对自己条目的编辑权。
3. **作废旧资格下的 GitHub 任务。** 未领取的任务在执行前失败并释放冻结。已在执行的任务在写入前检查原成员资格是否仍有效，失效时丢弃新结果并释放该次冻结。重新加入产生新资格，旧任务仍属旧资格。若需要继续同步，Creator 可以在自己的账号获准读取仓库后重新发起。
4. **保留处理记录。** 邀请、审批、退出或移除保留操作人与时间，供 Creator 回查。发给被移除成员的站内通知链接只显示本人可见的处理结果。

## 6. 数据与实施入口

| 改动 | 建议结构 |
| --- | --- |
| Ree 协作模式 | `ree.collaborationMode` 取 `solo` 或 `team`，存量默认 `solo`。另设 `acceptsJoinRequests`，默认关闭。协作模式独立于[个人品牌方案](personal-brand-implementation.md)的主页模式。 |
| 成员资格 | `ree_member` 记录 `reeId`、`userId`、`joinedAt`、`revokedAt`、`revokedBy`、退出方式及来源记录。以 `(reeId, userId)` 的部分唯一索引限制有效资格，另建按用户查询有效资格的索引。 |
| 邀请和申请 | `ree_join_intent` 记录 Ree、目标用户、类型、状态、说明、发起及处理人、处理时间和邀请过期时间。以 `(reeId, userId)` 的部分唯一索引限制 `pending` 记录，另建 Creator 队列和个人通知跳转所需索引。 |
| 知识归属 | 增加 `knowledge.createdBy`，用原 Ree 的 `ownerId` 回填存量条目，新增条目使用会话用户。GitHub 条目记录最近验证的仓库可见性。 |
| 处理任务与成本 | 复用 `knowledge_cost_run` 与 `credit_hold` 的关联，为 GitHub 任务保存授权账号、连接版本及当时的成员资格。成本快照区分归属与实际扣费人。兼容迁移前已排队的个人 Ree 任务，授权账号按原 owner 处理。 |

创建向导和草稿保存协作模式。`/rees` 分「我创建的」「与我协作」，后者直达知识页。现有批量发布、删除等选择集继续按 owner 筛选。`/rees/[id]/members` 提供成员、邀请和申请列表，Creator 在此审批。公开页提供申请入口，通知承接定向邀请的接受与拒绝。新增成员与加入流程 API 复用站内会话和同源写入检查，实际权限判断放在服务层。

实现时根据最新迁移日志生成增量迁移。在现有集成测试环境验证存量回填、默认值和排队任务兼容性。

## 7. 实施顺序与验收

1. **创建与成员流程。** 完成协作模式、成员数据、邀请、审批和通知。验收同一账号收到邀请后才能接受，申请人待审时读不到私有知识，重复批准只写一次成员和通知，撤回和批准并发时只发生一种状态变更。
2. **知识权限与协作入口。** 完成贡献者字段、权限服务、批量校验、目录边界、文件和测试会话授权。验收成员 A 可操作自己的条目，成员 B 只能读，Creator 可操作两者的条目。批量混入一条他人的知识时无条目被改动。退出后用旧文件链接、旧会话 ID 和旧 API 请求重新访问均被拒绝。
3. **GitHub 任务、可见性和账务。** 验收成员 A 可导入只有自己能读的仓库，Creator 无仓库权限时仍可编辑条目元数据及停用、删除，有自己的权限后可重跑。覆盖移除成员与后台提交并发、重新加入、连接变更、余额不足、失败退款和重复重试。私有或未知仓库无法通过发布、管理员恢复或启用操作进入公开回答、引用或发现检索。最后验证存量个人 Ree、公开问答与 Creator 收益路径。
